## 为什么优化与 profile 归因

- Quantizer：非重叠转置卷积可按相位展开为 dense projection，避免对应 cuDNN dgrad 与布局转换；只对 SM100 FP16 和明确适用条件启用，独立序列保留共享 codec 的状态接口。本次 C64 trace 中目标 direct-dgrad 路径消失；此前定形算子测试 6 组中 5 组 5→3 kernels，1 组 2→3。收益归因于算子/布局路径，未证明调度气泡减少。
- SM100：放开已有 fused sampler/tower 的架构门控，复用现有 Triton 实现。本次 C64 trace kernel 数由 428168 降到 302792；自然生成长度和调度会影响总数，不能仅凭总数精确量化某融合模块贡献。结合命中检查及吞吐提供机制证据；中文质量风险仍需保留。
- MoE：按真实专家形状调整 up/down 的配置、TMA 和分块，仅通过显式配置目录启用。本次 C64 `fused_moe_kernel` 累计 GPU 时长由 825.63ms 降至 574.49ms，kernel 总数/运行轨迹存在差异；这是诊断佐证，不是独立算子精确加速比。收益属于配置包，不能全部计给 TMA。

### 首包长尾

C1 诊断先重复第一参考音频暖机，再发送 16 条不同请求，避免预热所有参考音频掩盖首次处理开销。基线请求 index=2/4/6 的首包分别约 1.076/1.485/1.639 秒，预处理分别 1.017/1.429/1.584 秒；同段 CPU trace 中 cuDNN attention 调用分别长约 850/1188/1482ms。reference.snake 的 56 个 scope 累计仅约 2.6ms，不能把秒级长尾归因于 snake。基线也存在该现象；现有证据定位到参考预处理 attention 主机侧调用，尚不能区分内部初始化、规划与同步等细节。未清除共享磁盘缓存，不能称全冷启动 JIT 测试。

profile 与无 profiler 的吞吐分开报告。CPU 包围区间包含等待，不是 GPU kernel 执行时长；嵌套 attention scope 不能求和。GPU 活跃区间并集不是 SM 利用率。完整 8 点分析与 trace SHA 见 [profiles-analysis.json.gz](profiles-analysis.json.gz)，原始大轨迹保留于远程验证目录。

## 正确性与推进结论

- Quantizer：30 项定向检查通过，含 13 CUDA；实际优化路径、共享 codec 状态和 graph/eager bitwise 回放通过。16 条真实 codec 重建最大绝对误差 0.00323486328125、最小 SNR 53.2953dB，满足原 FP16 容差。可准备 Draft，质量结果和取舍完整披露。
- SM100：sampler/tower 69 项通过。完整套件仍有失败；严格 graph/eager 的两项失败在关闭 sampler/tower 的控制中也复现；不能因此宣布套件全通过。孤立 stateful capture 在 base/候选均通过，整套触发条件未完全解释。结合中文错误率风险，暂不作为可直接合并结论。
- MoE：真实 E256/H2048/I512/top8，M=1/8/16/32/64/128/256/512 的独立 CPU FP8 参考检查全部通过；最大参考行误差约 0.00317146，候选/默认最大行相对差约 0.00069151。最初初始化/测试脚本失败单独保留，不计为候选数值失败。可准备可选配置 Draft。
- 三条候选分别独立对同一 base，收益不能相加。当前服务不保留优化验证版本，已恢复原服务。上游 PR 创建此前被 GitHub App 资源权限阻止；用户要求先搁置权限问题，因此本轮不重复写入探测。
