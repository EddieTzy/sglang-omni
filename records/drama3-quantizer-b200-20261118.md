# Drama3 上采样：B200 单组服务初筛

结论：本轮高并发音频吞吐提高，但单并发和部分首音延迟回退；保留为“已测有收益或取舍”，不归成“无收益”，也不宣称全场景优化。只有一组顺序对照，没有重复运行的波动估计。

## 版本与方法

基线为 f17a438cd753248d70916700aa4dccd9e7feb098；候选为 [57c747e0](https://github.com/EddieTzy/sglang-omni/commit/57c747e0)，分支为 [perf/drama3-b200-quantizer-upsample](https://github.com/EddieTzy/sglang-omni/tree/perf/drama3-b200-quantizer-upsample)。记录的生产模型源码中，仅 channels_last_decoder.py 不同，公共启动命令和各并发点的请求文本集合相同，没有启用另两项候选改动。

硬件为单张 NVIDIA B200；PyTorch 2.14.1+cu130、SGLang 0.5.23、Triton 3.8.0、FlashInfer 0.7.2、CUDA 13、驱动 580.173.02。使用相同 Drama3 checkpoint、引擎容量64、async decode、overlap codec window、模型默认采样，max_new_tokens=2048 仅为安全上限，按自然 EOS 完成。使用固定修订的 SeedTTS EN 数据；每臂重启服务，各点预热 16/16/64 个请求，预热不计入正式统计。其他 GPU 工作在测量期间停止，完成后已恢复原服务并确认健康。

EN 数据来自 zhaochenyang20/seed-tts-eval-arrow@27f4c1adee83b5b29b7c4b375f6b976324bda308，Parquet SHA256 为 5849b41b49cae996328c06d2c5791717c3bafc369bddfa1ec4f86761bb8bc0ca。

用户将原计划改为只跑一组，因此仅保留 base→候选。后续重复在模型启动前取消，不计作测量，也不计入成功请求数。原始控制器的取消记录与两条有效测量记录一并保留。

## 为什么单并发下降

64 条请求的 completion token 数逐条一致，总数均为5877，平均音频长度均为4.264 s，因此不能用生成了更长音频解释本轮差异。

首音中位数仅从 72.5 ms 变为 74.2 ms，但有三个早期请求的首音时间分别额外增加 0.4031、0.8072、1.1830 s，合计2.3933 s，占全部首音增加总量2.5605 s 的约93.5%。逐请求总延迟差之和为2.2541 s，说明单并发的平均退化高度集中于这些首音长尾，而不是已证实的逐步解码普遍变慢。所有样本均保留，未剔除慢请求重新计算收益。

原服务性能轮次没有同步采集 profiler。最初关于“大 B×T 矩阵”的解释只是推测；后续局部轨迹显示 batch1 为 mm、batch16/64 为 bmm，不能直接声称实现已将所有 B×T 展平成一个大 GEMM。调用、算法选择与布局成本如何作用于服务关键路径仍需完整 profile。首次路径初始化、编译/加载、CPU 调度和 prefill 等仍是待检查因素，不能仅凭三条长尾认定其中某一个是原因。

## 正确性与质量边界

实际投影路径通过30项正确性检查，其中13项为CUDA检查，并覆盖 phase projection 的 CUDA Graph/eager 逐位一致性及共享 codec 的 stateful 使用。另有16组真实EN/ZH固定码本数值对照，确认选中2个投影，保持波形长度；最大绝对差0.00323486328125、最低SNR 53.2953 dB，均通过已有FP16 codec容差。

这些结果不能替代完整生成音频的 ASR、音色相似度、盲听或质量非劣效评估；本轮未完成这些评测。旧分支23.9%是不同基线的组合结果，没有加入本表。

## 基线如何复用

本次基线可用于同一代码基线、依赖、权重、硬件、公共配置、请求集、预热与无竞争负载条件下，其他独立优化的初筛。条件变化或需要确认小收益时应刷新基线。若在上采样候选上继续叠加另一个优化，应以上采样版本为新的增量对照，不能把组合收益全部归给后加入的改动。

后续方向是先定位首音长尾，再决定是否限制优化的启用条件。新的性能测量须经用户明确允许，并暂停其他GPU操作；本次已按用户新授权补充 GPU 诊断，服务性能初筛与诊断轮次分别记录。
